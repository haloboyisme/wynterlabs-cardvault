# V2.0.1 Release Closure Design

## Goal

Close WynterLabs CardVault V2 with verified account/community workflows, a
green complete test gate, a clean one-command installation, an encrypted
off-host recovery copy, accurate release evidence, and an immutable `v2.0.1`
release.

## Safety and cost boundaries

- Reuse the current V2 implementation, tests, Docker workflow, Proxmox scratch
  environment, backup scripts, and GitHub integration.
- Run focused tests only while repairing a known failure, then run one complete
  release gate after all changes are assembled.
- Test account lifecycle operations with a clearly named disposable member.
  Never change or delete the real owner account.
- Keep the private production installation available throughout.
- Restore only into an isolated scratch environment on alternate ports or a
  disposable Proxmox container.
- Do not move the existing `v2.0.0` tag. Publish the finished tree as the new
  immutable `v2.0.1` tag.
- Do not tag until every mandatory release-readiness item has evidence.
- Public files must not contain private addresses, usernames, emails,
  passwords, tokens, certificates, MFA secrets, or backup contents.

## Acceptance workflow

Use one disposable member for the live account/community checks:

1. Create the disposable member through the normal signup path.
2. Enable activity sharing, add one test card, verify the safe Home activity,
   disable sharing, and verify the member activity disappears.
3. Change the disposable member email, verify the session is revoked, and sign
   in with the new email.
4. Enroll optional MFA for the disposable member, then use the owner account to
   reset that member's MFA and verify existing member sessions are revoked.
5. Request deletion, cancel it, request it again, verify it in the owner Admin
   table, and approve deletion.
6. Verify the disposable member can no longer sign in and the owner account is
   unchanged.

## Test and installation evidence

The final local gate includes all API tests, all web tests, API linting,
TypeScript checking, the production web build, shell syntax checks, diff
whitespace checks, and a public-source secret scan. The latest standalone
installer is then tested from a clean clone in a disposable container with
generated secrets, owner setup, health, backup, and isolated restore checks.

## Recovery evidence

Create a new post-verification backup, verify its checksums and isolated
restore, encrypt the backup for off-host storage, copy it outside CT 102, verify
the copied checksum, decrypt into a temporary directory, verify the decrypted
archive checksums, then remove only the temporary decrypted copy.

## Release evidence

Update `VERSION`, installation commands, changelog, and the readiness checklist
to `2.0.1`. Commit the exact tested tree, deploy it privately, obtain owner
acceptance, update GitHub branch `v2`, create immutable tag `v2.0.1`, and verify
the branch and tag resolve to the intended release commit.
